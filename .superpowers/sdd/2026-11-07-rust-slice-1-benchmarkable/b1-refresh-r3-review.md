None becomes Absent and may enter the 30-second negative cache. A new DB key can therefore be refused until the next successful full rebuild, normally the gateway's 500-ms poll plus read/scheduling time; rebuild bumps generation and invalidates that negative. If polling is stopped/failing, fallback can retry after the 30-second negative TTL (subject to the existing read budget). This conservative behavior already existed in the CAS version; no new permanent invisibility introduced. Full rebuild's key publication is unaffected by the negative cache.

Production release uses panic=abort, so no later publisher exists after an abort; the recovery claim applies to unwinding builds. No separate poison-injection test run.

## Microbenchmark assessment (read only; not executed)

- Both files install the product mimalloc allocator and all three tests are #[ignore], so normal test runs do not measure performance. preparation_perf measures request construction + dispatch preparation + immediate unpolled-stream destruction, using wall time; it does not send/decode/render. Its construction control covers common::chat only, not all Request fields, so subtraction is approximate “dispatch plus surrounding preparation”, not isolated dispatch nanoseconds.
- nonstream_perf measures Anthropic ingress→custom dispatch→in-memory Replay→decode→collect→Anthropic buffered render/serialize, including assertions, IDs, allocations and teardown. Replay bypasses real HTTP/network and is immediately ready; current-thread Tokio keeps request-thread schedstat accounting meaningful. It omits auth/rate admission, server framing, sockets/TLS, backpressure and completion accounting. Dispatch still enqueues Begin records to a real writer: “no completion row” is accurate, “no persistence work at all” would not be. Other-thread writer CPU is excluded from request-thread CPU.
- The reported allocator-corrected, CPU-pinned interleaved results (2448.5→2398.8 preparation; 12696→12495 buffered CPU ns/request) support **no observed slowdown for these specific warm in-process fixtures at the measured checkpoint**, not proof that every HEAD path is no slower. The report dates those comparisons to the part-1 checkpoint rather than demonstrating a final-b66c rerun. No confidence interval or equivalence margin is established. A ~3% gateway difference could involve real HTTP client/server framing and syscall cost, socket readiness/scheduling, concurrent allocator/cache contention, writer/completion/rate-limit work, background tasks, CPU frequency/measurement variation, or interactions absent in Replay. These measurements do not identify which cause applies or waive the gateway benchmark.
