Both gateways are measured black-box by scripts/bench-gateway.ts: the gateway is a process started from an argv, set up through the CLI, driven by `oha` against a scripted upstream, with CPU pinning (`taskset`) and per-scenario throughput, latency, CPU per request and RSS. ## What to build

1. A provider table in the harness. Each entry describes one upstream provider variant: an id, how its credential is created (CLI where the CLI can do it; otherwise the way conformance/e2e/anthropic.ts seeds it), how a model target for it is declared, which scripted upstream serves it and on which origin. Entries to deliver now — these are the provider variants that exist in BOTH gateways today:
   - `custom-chat`  — custom provider, chat-completions protocol (what exists today);
   - `custom-responses` — custom provider, Responses protocol;
   - `anthropic-key` — Anthropic provider, API-key credential;
   - `anthropic-oauth` — Anthropic provider, OAuth credential whose access token stays valid for the whole run (no refresh during measurement; whatever the gateway asks of the token/usage endpoints at boot must be answered by the stub).
   The frozen gateway has more providers (openai/codex, antigravity, grok, kimi, kilo, muse, qoder) that the Rust gateway does not have yet. Do not build stubs for them now; make adding one a matter of adding a table entry plus a scripted upstream, and write in the report exactly what a new entry needs.

2. Scripted upstreams for each wire the gateways speak upstream: chat-completions SSE (exists), Responses SSE for `custom-responses`, Anthropic Messages for the two Anthropic variants — whatever the gateway actually requests (find out from the frozen codec whether it always asks upstream for a stream; serve exactly that), with correct usage figures so request logging and pricing do real work. Same conventions as the existing upstream: behaviour from the model name `mock-c<chunks>-d<delayMs>` if the provider lets an arbitrary upstream model name through, otherwise another value the gateway forwards untouched (say which); instant replies written in one write; frames encoded once and replayed; several copies on one port; a separate process pinned to the upstream CPUs. The upstream must never be the ceiling: show for each stub that it alone serves several times the gateway's best rate (drive it directly with `oha`).
   The Anthropic provider's origin is fixed (https://api.anthropic.com), so those variants need TLS and a hosts override in a private namespace, as conformance/e2e/anthropic-ns.sh does. Put that in a wrapper script (scripts/bench-matrix.sh or similar) so one command runs the matrix; check that `taskset`, `/proc` sampling and `oha` still work inside the namespace, and that both gateways trust the stub's certificate through the environment only.

3. The scenario matrix, generated from the table rather than written out by hand: for each provider variant × each ingress (`/v1/chat/completions`, `/v1/messages`, `/v1/responses`) × each response mode (non-streaming, streaming): one scenario, 64 clients, one upstream chunk. Plus, per provider variant: one single-client scenario (pure per-request overhead; streaming through the provider's nearest ingress) and one long-stream scenario (2,000 upstream chunks, 16 clients, streaming). Names of the form `<provider>.<ingress>.<mode>` (`anthropic-key.messages.stream`, `custom-chat.chat.json`, `anthropic-key.overhead-c1`, `anthropic-key.chunks-2000`).
   - Selected with a flag (`--matrix`), combinable with `--only` accepting exact names and simple prefixes/globs (`--only 'anthropic-*'`, `--only '*.responses.*'`). Without `--matrix` the existing scenario list and its numbers stay exactly as they are — earlier baselines must remain comparable. Do not change what the existing scenarios measure.
   - A combination a gateway cannot serve must be reported as `unsupported` with the reason (status and error code seen in the smoke request), never silently dropped and never counted as a failure of the run. A smoke request per scenario before measuring, as today.
   - Every scenario keeps the existing integrity checks (status distribution, request-log rows written, writer drops) — a scenario in which the gateway answers errors quickly must not look fast. Add a check that the response for each scenario has the expected shape for its ingress and mode (content type, and that the content text made it through).
   - Output: the JSON gains the provider/ingress/mode fields; the markdown gets one table per provider variant (rows ingress × mode; columns req/s, p50, p99, CPU ms/req, RSS), and a comparison mode that takes two result files (for example TS and Rust, or base and head) and prints the ratio per scenario with the number of rounds, medians and min–max per side — no percentage without the spread next to it.

4. A runner for interleaved rounds (base/head or ts/rust alternating, N rounds, results per round kept), like /tmp/opencode/bench-gate/run.sh does for the two existing scenarios — committed under scripts/, parameterised, with the uptime/load recorded before and after and a refusal (overridable) to start when the 1-minute load average is above a threshold.
