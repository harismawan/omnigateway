# Benchmark diagnosis — measured Rust 327f240f

## 1. Anthropic connections: reproduced; root cause confirmed (high confidence)
- Counts below aggregate JSON + streaming ingress, each with 256 warm-up and 256 measured requests, plus smoke/verifier requests. Sequential concurrency=1; concurrent=32. All final count runs passed response checks. No timing comparisons are evidence here.
- Rust baseline Anthropic: **1,030 connections / 1,030 requests sequential; 1,028 / 1,028 concurrent**; zero checkins/releases. Independent stub peer-port counts agree.
- Rust custom HTTP control: **2 / 1,028 sequential; 32 / 1,028 concurrent**; all 1,028 responses released and checked in in each run.
- Frozen TS binary Anthropic: **2 / 1,030 sequential; 31 / 1,028 concurrent**, counted by upstream peer ports in isolated namespaces.
- Cause: `crates/omni-providers/src/anthropic/decode.rs:303–311,344` emits `StreamEvent::End` for `message_stop` but returns `Flow::Continue`. `crates/omni-gateway/src/dispatch.rs:843–844` breaks on End, dropping EventStream with its body still owned. The next `next_chunk()` that would release the connection never happens.
- In contrast, custom decoder returns `Flow::Stop` (`custom/decode/chat.rs:292,323`), invoking `adapter.rs:310–312,332–336` and `finish_if_ready()` before its pending End is delivered.
- Actual TLS stub response: **HTTP/1.1, Content-Length: 722, no Connection header**; not chunked. `http/body.rs:546–547` permits reuse; at the body boundary `Length(0)` needs another read-next invocation to become Done/release (`:268–272,179–185`). Thus neither trailing chunk arrival nor TLS session tickets explains this baseline failure: checkout never has an idle TLS connection to inspect.
- Confirming scratch change: return `Flow::Stop` immediately after Anthropic message_stop enqueues End. Same stub: **2 / 1,028 sequential; 32 / 1,028 concurrent**, with 1,028 releases/checkins each. No pool or TLS changes. This also demonstrates that `Conn::still_idle()` does not inherently reject this stub's TLS connections.
- Additional fixture experiment, keeping that decoder change: send SSE in a chunked response and delay HTTP termination 20 ms. **516 connections / 516 requests, zero releases/checkins**, both ingress modes correct. This independently reproduces the hypothesized `finish_if_ready()` limitation (`http/body.rs:151–175`): a Pending read closes the body instead of awaiting termination. The original stub does not exercise this limitation.
- Classification: **product lifecycle defect**, exposed by the harness, not caused by peculiar close headers. The decoder/dispatch mismatch also applies to real Anthropic message_stop; real-provider connection counts were not measured. TLS makes lost reuse more expensive but is not the lifecycle cause. No real-provider framing assumption is needed for this conclusion.
- TS reference path: `packages/providers/src/http-client.ts:132–155` uses node:https plus IncomingMessage/Readable.toWeb; `sse.ts:139` releases its reader lock. Observed frozen-binary counts establish reuse for this fixture; real delayed-framing TS behavior was not tested.
- Scope: Rust token refresh uses `response.body.text().await` (`crates/omni-gateway/src/refresh.rs:240`), which reads to HTTP completion (`http/body.rs:198–213`), bypassing this SSE defect. No Rust `/api/oauth/usage` implementation was found in the measured crates; TS usage flows consume buffered auth responses through `packages/control/src/oauth/pluginFlow.ts:300`. Neither token refresh nor usage polling was connection-count tested.
- Smallest fix for the measured defect: stop the Anthropic decoder on successful message_stop before returning End. For robust streaming reuse, also provide byte/time-bounded asynchronous completion draining, with cancellation/error paths closing the socket; do not return unread framing to the pool. Avoid unbounded background drain tasks.
- Regression must count accepted upstream sockets for successive and concurrent JSON/SSE gateway calls over TLS, including Content-Length and delayed chunked terminators; assert response correctness, reuse after clean completion, and closure on truncation/cancellation/drain timeout. A decoder-only test misses the dispatch lifecycle.
- Not established: attribution of the original throughput/tail distribution or RSS growth to this defect, TLS-resumption allocation behavior, or behavior against live Anthropic. Counts establish repeated handshakes, not a memory leak.

## 2. Request-log loss: policy reproduced; particular stall remains unidentified
- Original `bench-real-2026-11-14/head/3.json`: **1,421,200 events = 1,403,988 committed + 17,212 dropped + 0 failed**; 710,559 answered including warm-up, 701,996 done, 78 pending, 8,563 missing done rows. All 538,983 measured responses were HTTP 200 with correct size. Events and rows differ because Begin/Finish are independently queued; Finish can upsert a row (`crates/omni-store/src/writer/sql.rs`).
- `crates/omni-store/src/writer/task.rs:118–124,546` creates a **131,072-event Tokio bounded queue**, max batch 4,096, 200 ms interval. `:353–390` uses **try_send**, drops the incoming event on Full **or Closed**, increments counters, and returns false. It does not evict oldest events, await capacity, or retry dropped events.
- Gateway callers ignore that boolean (`crates/omni-gateway/src/dispatch.rs:669`, `finish.rs:144`). Successful client requests therefore need not have durable log rows. One batch writes at a time via spawn_blocking (`writer/task.rs:858–873`); events accumulate while the writer cannot consume them.
- Deterministic reproduction: existing `crates/omni-store/tests/writer.rs:470–510`, current-thread runtime with consumer unable to run during production: capacity **4**, ten sends → **4 accepted/committed rows, 6 dropped**. One post-close send raises drops to 7. Release-mode test passed.
- Confirming scratch change: only capacity **4→10** and expected assertions changed; same blocked-consumer schedule → **10 accepted/committed rows, 0 overflow drops**; post-close send still drops once. Test passed. This isolates bounded queue overflow independently of SQLite faults; increasing capacity merely moves the threshold.
- Most plausible condition in head/3 (**inference**): a transient writer-service deficit, such as a disk/WAL/checkpoint stall, exceeded available queue headroom. The process continued and later scenarios lost nothing, making permanent closure implausible. `failed=0` means no permanently failed batches, not absence of slow/busy writes.
- The config has a separate 20 ms passive checkpointer and a 10,000-page in-commit checkpoint backstop (`writer/task.rs:68–88,122–123,505–517,541`); WAL growth is not bounded by that trigger. These are possible stall mechanisms, not measurements of this incident.
- **Cannot distinguish** cold-start allocation, WAL growth/checkpoint/fsync, scheduler delay, or another transient. The failed scenario has `metrics:null`; its diagnostics and round log contain no queue-depth, batch-duration, WAL-frame, or disk trace. The original per-gateway log directory is gone. Other rounds also began cold and did not drop. No evidence singles out first-use allocation.
- Harness post-run reads start only after load reporting (`scripts/bench-gateway.ts:1134–1167`), close statements/connections, and may affect backlog recovery/checkpoint progress. They cannot explain overflow already occurring during load, but drop timestamps were not retained, so their contribution to late draining cannot be excluded. No positive evidence identifies a harness-caused drop.
- Classification: **product's deliberate lossy overload policy**, violating a lossless-log expectation; historical stall trigger unresolved. No demonstrated harness artefact.
- TS store writes synchronously inside async methods: `packages/store/src/sqlite/usage.ts:304–314,350–368`; gateway awaits `usage.begin/append` (`apps/gateway/src/logging.ts:169,310`). SQLite stalls block the JS execution path, reducing admitted throughput rather than overflowing a separate log queue. There is no analogous bounded queue/drop policy. DB exceptions can still lose logs and are caught/reported; this is not an unconditional durability guarantee.
- Operators get rate-limited WARN **“request log writer is full; events dropped”**, count since warning and rawCount total (`writer/task.rs:246–265`), and shutdown WARN **“request log writer lost events”** (`omni-gateway/src/lib.rs:614–620`). Warning test passed. Original harness `writerDropped=17212` confirms the shutdown log was observed. Runtime warning may be delayed while the writer is stalled.
- Smallest correctness fix if logs must be lossless: await bounded queue capacity for request-log events and propagate admission/shutdown failure, so overload backpressures requests; retain batching. Merely enlarging the queue or suppressing the harness check is insufficient. Preserve separately intentional nonblocking policies for other event types.
- Regression: hold a SQLite write lock/otherwise block consumption, produce more than queue capacity, then release it; assert backpressure, every acknowledged request has exactly one completed row, zero drops, correct rollups, and clean cancellation/shutdown. Add queue high-water and batch/checkpoint-stall diagnostics to identify future incidents.
