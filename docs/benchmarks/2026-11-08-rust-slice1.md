# Gateway: Rust slice 1, single process

The first benchmarkable slice of the Rust gateway (single mode, SQLite) is
measured here against the [TypeScript baseline](2026-11-07-ts-baseline.md) and
against the spec's targets (`docs/superpowers/specs/2026-11-07-rust-gateway-migration-design.md`,
§"Targets"). The raw output is in
[`2026-11-08-rust-slice1.json`](2026-11-08-rust-slice1.json): the summary, the
three runs in full, and the shedding runs quoted below.

Slice 1 has no cluster mode, because Rust has no Postgres or Redis store yet.
The cluster targets are therefore not measured here.

## Read this first: the numbers are zero-drop numbers, capped at 20 000 req/s

The TS gateway writes every `request_logs` row synchronously, so its baseline
loses no rows. The Rust gateway writes them in batches from a writer task with
a bounded queue. When that queue is full it sheds (the spec's overload
behaviour), so a Rust run can look fast because it skipped work TS did. That
comparison is not like for like. The earlier version of this document
published such numbers: chat-stream 51 k req/s and anthropic-json 54 k, from
runs that dropped most of their rows. Those numbers are withdrawn.

The bench now checks, for every scenario, that every answered request has a
`done` row, that no row is left `pending`, and that the gateway logged no
writer drops (see "How it was measured"). Any of these fails the run.

- **The table below is the median of three full runs** (min–max in brackets).
  Every scenario in all three runs has 0 rows missing, 0 pending and 0 writer
  drops.
- **Each duration scenario is capped at 20 000 req/s** (`--rate 20000`, i.e.
  `oha -q`). That is the highest round rate at which three runs in a row came
  out with zero drops (see "The writer's capacity"). Uncapped, the gateway
  serves ~50–57 k req/s on these 4 cores, but its writer then sheds 40–60 % of
  the rows. The req/s column is therefore the cap for the five 64-client
  scenarios, not their ceiling. agent-100k, many-chunks, overhead-c1 and
  held-streams run below the cap, so their numbers are the gateway's own.
- **The latencies are at 20 k req/s, not at saturation.** That puts Rust's
  p99 below what it was in the old saturated runs.

## How it was measured

The rig and method are the baseline's:

- **Script:** `scripts/bench-gateway.ts`, black-box.
- **Upstream:** two `bench-gateway-upstream.ts` processes on one port, reached
  through a `custom` credential.
- **Host:** i5-13400, 8 vCPUs, Linux 6.12, running as a KVM guest. Gateway
  pinned to cores 0-3, upstream to 4-5, `oha` to 6-7.
- **Duration:** 20 s per scenario after a 3 s warmup, with `OMNI_LOG_LEVEL=warn`.
- **Setup:** done by the TS `omni` CLI. The CLI is not ported, so `omni keys
  list` still measures TS.
- **Build:** `d6933714`: release profile, fat LTO, one codegen unit,
  `panic=abort`, mimalloc v2.

```sh
cargo build --release -p omni-gateway
bun scripts/bench-gateway.ts --gateway target/release/omnigateway \
  --cli "bun apps/cli/src/index.ts" --rate 20000 --out run-N.json   # × 3
```

What the bench does now that it did not before (`fix(bench)` commits):

- **Row accounting per scenario.** After each scenario, the bench waits until
  the log stops changing, because the writer may still be draining a queue
  built up during a disk stall. It then counts the `request_logs` rows whose
  `at` falls in the scenario's window:
  - `missing`: answered requests without a `done` row;
  - `pending`: rows never finished;
  - writer drops: the `count=` of the gateway's rate-limited "writer is full"
    warnings stamped inside the window, plus the shutdown total.
  
  If any of these is non-zero, the row is flagged `⚠ DROPPED` and the run gets
  a warning at the top. The cancel scenarios file a 499 row for each
  abandoned request, which can hide a missing row from `missing`. The drop
  count catches that case.
- **`-t 30s`** on every scenario that has no timeout of its own. A wedged
  keep-alive connection becomes a counted error instead of an `oha -w` that
  never returns. held-streams and the cancel scenarios keep their own
  timeouts.
- **Host calibration.** Before the run, a fixed CPU-bound loop is timed on
  each vCPU, first alone and then on all eight at once. During each scenario
  the bench samples the gateway cores' MHz, the busy cores used by processes
  outside the bench (`foreignCores`), and the per-thread CPU and run-queue
  time of the gateway.
- **`--rate N`**: caps every duration scenario at N req/s.

Notes on the comparison:

- **CPU per request at 20 k is higher than in a saturated run.** An idle
  worker parks and wakes again, and that overhead is spread over fewer
  requests. Uncapped, chat-stream costs 0.062 ms/req (53 k req/s, with
  shedding). The capped figure is the honest one for "every row written".
- **early-cancel's CPU per request is not comparable with TS.** The
  denominator counts every attempt `oha` made, including requests that never
  reached the gateway. With the cap, Rust completes 95 % of attempts (TS: far
  fewer), so it does much more work per attempt. Its 499 rows: 399 k `done`
  rows for 380 k answered requests, because each abandoned request is filed
  as a 499.
- **held-streams TTFB.** p50 522 ms (TS 827), p99 1541 ms (TS 1553).
- **agent-100k** is named for a ~100 KiB transcript, but `agentBody()`
  serializes to 53 KB.

### Missed: held-streams RSS peak, 82 MiB against ≤ 80

- **Measured.** 82 MiB peak (81–88), from 49–54 MiB at the start of the
  scenario. The pre-change build at the same 20 k cap measured 78 MiB.
- **What the writer changes cost.** About +4 MiB.
  - The queue holds up to 131 072 events of 344 bytes each. It allocates in
    blocks only as it fills, but mimalloc keeps freed pages for a while.
  - The fixed-size statement cache is small.
  - Statements sized per batch had pushed this to 95–103 MiB before
    `fc93a287` fixed them (see the report).
- **Cause, as before: retained allocator memory.** The scenario starts with
  the heap the earlier scenarios left behind.
  - With glibc malloc the peak was 66 MiB, but CPU was 30–45 % higher
    everywhere, and many-chunks missed its target by 50 %.
  - With `MIMALLOC_PURGE_DELAY=0` the peak was 63 MiB, at 5–10 % more CPU on
    the chunk-heavy scenarios.
  - Both figures are from the previous round's table, which was measured
    unchanged.
- **What closing it would take.** Any one of these:
  1. purge mimalloc's free pages at once. That needs a vetted wrapper crate
     for `mi_option_set`, which the workspace's `forbid(unsafe_code)`
     excludes, or an environment default in the Docker image and systemd
     unit.
  2. Shrink the per-stream footprint, ~25 KiB per held stream today. Two
     candidates are the 16 KiB read reservation per upstream connection, and
     boxing the 144-byte `StreamEvent` in the pending queues.
  3. Box `WriteEvent::Log`'s `RequestLog`. At 344 bytes per queue slot, a
     slot would shrink to ~16 bytes plus the heap row, which cuts what a full
     queue can hold.

  None of these was attempted here. The target is reported as missed, not
  lowered.

## The writer's capacity

The spec's shed path is for real overload, such as a stalled database. It is
not meant to fire at the gateway's own throughput. Before this round it did.

### What changed

- **4096-event batches** instead of 512. `request_logs` has a random primary
  key (`req_<uuid v4>`), so each row dirties one more B-tree leaf, and bigger
  batches share those pages and the per-transaction cost.
- **A 10 000-page `wal_autocheckpoint`.**
- **No read-back.** Roll-ups and limiter debits are computed from the rows the
  batch wrote. The TS comparison test still holds the rows equal.
- **Statements with fixed row counts** (256/64/16/4/1), reused across batches.
- **A checkpoint thread** running `wal_checkpoint(PASSIVE)` on its own
  connection every 20 ms. Before it, a batch in five paid for a checkpoint
  inside its commit, at 50–935 ms each.
- **A 131 072-event queue.** It holds about 3 s at 20 k req/s, enough to ride
  out the 0.5–1 s XFS log flushes seen on this disk under the WAL's fsync.

The Begin and Finish of one request that land in the same batch were already
written as one final row before this round (one upsert per touched id).

### Why the cap is 20 k and not the gateway's ~55 k

- **The gateway shares 4 cores with its writer.** At ~53 k req/s the request
  workers use all four. The writer's blocking thread then gets ~40 % of a
  core, and its share falls as the run goes on.
- **Each row costs more as the database grows.** The random-UUID primary key
  outgrows the page cache as `request_logs` fills: 2.6–2.8 GB after one full
  run. A batch then re-reads leaves from the OS cache with `pread` and
  rewrites them through the WAL.
  - Measured on one free core: 30–38 µs of CPU per row on an empty database,
    42–60 µs on a 3 M-row one.
  - With a time-ordered key, the same writer and load committed 80–120 k
    events/s, against 33–48 k with random ids, and the rate stayed flat as
    the table grew.
- **The disk stalls.** The WAL fsync sometimes waits 0.5–1 s on XFS's log.
  The queue now rides these out.
- **Measured zero-drop ceilings.** On the final build, three 20 k runs in a
  row had zero drops. Three 25 k runs on intermediate builds (before the
  bigger queue) all dropped 0.05–1.3 M events in the later scenarios. A 30 k
  cap dropped 300–400 k rows per scenario. 25 k was not retried on the final
  build, so the true ceiling lies somewhere between 20 and 25 k.

**What closing the gap would take.** Each of these is a design call, not a
tuning knob:

1. **A time-ordered request id**, for example a UUIDv7-shaped `req_`. Inserts
   then go to the right edge of the primary key, and the measured gain is
   2–3×.
   - It changes an id format that TS defines (`req_${crypto.randomUUID()}`),
     which the conformance masks check, and that clients see in
     `x-omni-request-id`.
   - The id's first 48 bits would reveal when the request started.
2. **Give the writer its own core**, outside the gateway's four. That
   changes the rig comparison with TS, which ran its writes on its own
   cores.
3. **Let the request path wait for queue space instead of shedding.** That
   slows requests down to the writer's rate. The spec makes this the
   builder's call ("shedding traffic instead is defensible") and chose to
   shed.

## Throughput was bimodal: the cause was the host, not the vCPU

On the same binary, chat-stream once ran at 49 k req/s and at 23–27 k in other
runs. This round found the cause.

- **Load from another process on the same guest.** A headless Chrome
  (Playwright, `--use-angle=swiftshader-webgl`) was rendering WebGL in
  software at 4.3–5.5 cores, unpinned, so it ran on all 8 vCPUs. `uptime`
  showed a load average of 6–8.
  - While it ran: chat-stream 29.9–31.1 k req/s.
  - With Chrome reniced to 19: 38.8–42.1 k, interleaved on the same binary
    minutes apart.
  - After Chrome's GPU process went idle by itself (00:44 UTC; it was
    restarted and has used ~0 % since): 53–60 k.

  The "quiet host" of the earlier runs was quiet only some of the time. Every
  run in the table above recorded 0.15–0.9 foreign cores, mostly the bench's
  own CLI and Bun overhead.
- **Not the vCPU placement.** With the guest quiet, the calibration loop
  times every vCPU within ±2 %: alone 468–500 ms, all eight at once
  527–582 ms, in all three runs. chat-stream on cores 0-3 against 4-7,
  alternated three times: 48.9–50.6 k against 47.9–50.5 k. Neither set is
  faster. The rig is kept on 0-3, and no second column is needed.
- **Not CPU frequency.** `/proc/cpuinfo` reports 2496 MHz on every core in
  every sample, idle and under load. That is the KVM guest's fixed TSC value,
  so it says nothing about the host's turbo state.
- **Not thermal.** A 4.5 s sustained spin on one core matched its 0.45 s
  runs, and the calibration's "all at once" time stayed stable across hours.
- **Shedding itself also inflates req/s.** A shedding run skips most row
  writes. That frees part of a core for the request path, so it looks faster
  than a run that writes everything. That is why the bench now refuses to
  count such runs.

The calibration and the foreign-load sample are now in every run's JSON
(`calibration`, `foreignCores`), so the next disagreement between two runs can
be traced to its cause.

## Caveats

- Loopback only, as for the baseline.
- The disk is a QEMU virtual HDD on XFS. Its fsync stalls set part of the
  writer's ceiling. On a real SSD, the zero-drop rate would be higher.
- `omni keys list` measures the TS CLI.
