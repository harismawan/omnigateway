# Gateway: Rust slice 1, single process

The Rust gateway's first benchmarkable slice (single mode, SQLite), judged
against the [TypeScript baseline](2026-11-07-ts-baseline.md) and the spec's
targets (`docs/superpowers/specs/2026-11-07-rust-gateway-migration-design.md`,
§"Targets"). The raw output is in
[`2026-11-08-rust-slice1.json`](2026-11-08-rust-slice1.json).

Cluster mode is not part of slice 1, because Rust has no Postgres or Redis
store yet, so the cluster targets are not measured here.

## How it was measured

The rig and method are the same as the baseline's:

- **Script.** `scripts/bench-gateway.ts`, black-box.
- **Upstream.** Two `bench-gateway-upstream.ts` processes on one port, reached
  through a `custom` credential.
- **Host.** i5-13400, 8 cores, Linux 6.12. The host is a KVM guest.
- **Pinning.** Gateway on cores 0-3, upstream on 4-5, `oha` on 6-7.
- **Duration.** 20 s per scenario after a 3 s warmup, with `OMNI_LOG_LEVEL=warn`.
- **Setup.** Done by the TS `omni` CLI. The CLI is not ported, so `omni keys
  list` below still measures TS.

```sh
cargo build --release -p omni-gateway
bun scripts/bench-gateway.ts --gateway target/release/omnigateway \
  --cli "bun apps/cli/src/index.ts" --label "rust-slice1 single @ <sha>" \
  --out docs/benchmarks/2026-11-08-rust-slice1.json
```

`--gateway` may now be relative. Its program path is resolved against the
repo root, because the gateway runs with its cwd in the bench root.

**Build.** `4686ce68`: release profile, fat LTO, one codegen unit,
`panic=abort`, mimalloc v2.

**Host noise, which matters for the tails.** For most of this work a headless
Chrome on the same host used about 4.3 cores, unpinned. While it ran, even a
three-process Unix-socket ping-pong with no gateway at all showed a 4.8 ms p99
(a `/tmp` script, see the task report). The table below was recorded after
that load stopped, at a load average under 3. A second full run at the same
commit (`/tmp/opencode/final4.json`) agreed with it to within 3% on every
scenario.

For comparison, two loaded-host runs of the same code gave:

| | overhead-c1 p99 | chat-stream | held-streams RSS peak | many-chunks CPU | boot |
|---|---:|---:|---:|---:|---:|
| loaded host (two runs) | 3.6–3.7 ms | ~24k req/s, p99 8.8 ms | 85–88 MiB | 1.4–1.64 ms/req | 33 ms |

The TS baseline was recorded on 2026-11-07. It is not known whether that load
was present then.

On the loaded host, three targets were missed:

- overhead-c1 p99 was 3.6–3.7 ms;
- boot was 33 ms;
- many-chunks was 1.64 ms/req in the first loaded run (1.4–1.55 in later
  interleaved ones).

Why those tails are the host and not the gateway is shown below.

### Missed: held-streams RSS peak, 85 MiB against ≤ 80

- **Measured.**
  - Final run: 85 MiB peak, from 61 MiB at the start of the scenario.
  - Repeat run: 84 MiB, from 53.
  - Before the allocator change (glibc malloc, first Rust run): 76 MiB.
- **Cause: the allocator's retained memory.** Same build, held-streams after
  chat-stream, agent-100k and many-chunks (8 s each):

  | allocator | held-streams peak | chat-stream CPU | agent-100k CPU | many-chunks CPU |
  |---|---:|---:|---:|---:|
  | glibc malloc | 66 MiB | 0.105 | 1.091 | 2.258 |
  | mimalloc v3 | 78–88 MiB | 0.076–0.082 | 0.66–0.78 | 1.49 |
  | mimalloc v2 (shipped) | 74–82 MiB | 0.069–0.077 | 0.66–0.89 | 1.52 |
  | mimalloc v2, `MIMALLOC_PURGE_DELAY=0` | 63 MiB | 0.084 | 0.781 | 1.64 |

  - glibc malloc fits the memory target but misses many-chunks by 50%, and
    costs ~30–45% more CPU everywhere.
  - Of the mimalloc options, v2 is the better default.
- **What closing it would take.** Any one of these:
  1. **Purge mimalloc's free pages at once.** `MIMALLOC_PURGE_DELAY=0` gives
     63 MiB, at about 5–10% CPU on the chunk-heavy scenarios.
     - The crate exposes this only through the environment, or through
       `mi_option_set`, an `unsafe extern` call that the workspace's
       `forbid(unsafe_code)` excludes.
     - So it would need a small vetted wrapper crate, or a documented
       environment default in the Docker image and systemd unit.
  2. **Shrink the per-stream footprint** (~25 KiB per held stream today):
     - smaller read buffers per upstream connection (16 KiB `reserve` each);
     - boxing the 144-byte `StreamEvent` in the pending queues.
     - Not attempted in this task.

  This is reported, not lowered.

### Tail latency on a loaded host (overhead-c1 p99)

The stall was traced as follows:

- **Inside the gateway.** Request stages timestamped in a throwaway build:
  - auth, body read and ingest take < 30 µs, even in slow requests;
  - the whole delay falls between dispatch and the first frame.
- **Inside the HTTP client.** The upstream write takes 5–10 µs; the
  head-arrival wait takes 0.8–3 ms on the slow requests.
- **Not the Bun upstream.** A minimal Rust upstream
  (`examples/mini_upstream`) behind the gateway still gave p99 3.2 ms.
- **The host.** A three-process Unix-socket ping-pong with the same pinning
  and no gateway (client on core 6, middle hop on 0, far end on 4) gave a
  **4.8 ms** p99 while the Chrome load ran, and **0.14 ms** once it stopped.
  The gateway's p99 fell from 3.7 to 0.26 ms at the same time, with no code
  change.
- **Ruled out by measurement:**
  - tokio worker count (1, 2 and 4 workers: same tail);
  - SQLite writer commits (DB on tmpfs: same tail; slow requests spread
    evenly over the 200 ms batch window);
  - Nagle (`TCP_NODELAY` is set on both inbound and upstream sockets);
  - allocator purge (the same tail with glibc malloc).

### Boot: the KDF's share

- PBKDF2-SHA256 at 210,000 iterations takes 21–24 ms in release on this CPU
  (sha_ni). That is 70–80% of boot.
- The iteration count is a storage contract (`omni-crypto`) and is not
  changed.
- The key is now derived on a blocking thread while the store opens and the
  pending sweep runs, which overlaps about 4 ms.
- What remains is about the KDF plus ~3 ms of runtime start and listen. So the
  floor on this host is about 25 ms, and on a loaded host the KDF alone
  approaches 30.

## What changed

Stage profile on the bench payloads (`examples/stage_profile`, µs per
request, release with symbols):

| stage | before | after |
|---|---:|---:|
| depth pre-scan (`depth_bound`) | 77 | 23 |
| parse (`deep::parse` → `parse_bounded`) | 190 | 53 |
| validate + IR (`anthropic::parse`) | ~270 | 133 |
| ingest total, agent body | 536 | 215 |
| `build_request` (wire + jsjson) | 121 | 84 |
| SSE parse, 2000-chunk reply | 971 | 100 |
| chat decode, 2000-chunk reply | 2009 | 458 |
| Anthropic egress encode, 2000 events | 129 | 122 |

Changes, in commit order:

1. **mimalloc as the global allocator.**
   - Under load, glibc malloc's arena locks and free lists were a third of a
     streaming request's CPU (SIGPROF sampler: `__lll_lock_*`, `_int_malloc`,
     `_int_free`).
   - Effect: many-chunks 6.0 → 3.6 ms/req.
2. **SSE parser.**
   - UTF-16 units are counted only once the buffer holds more than
     `MAX_RECORD_CHARS` bytes, since units never exceed bytes.
   - The newline search uses `memchr`.
3. **Custom chat decoder.** A typed serde parse of the five fields it reads,
   with every unsure case falling back to the generic `Value` path. A test
   decodes each case both ways. Fields are boxed to keep serde's moves small.
   - Effect: many-chunks 3.1 → 1.2–1.4 ms/req.
4. **Ingest.**
   - The depth bound is computed once (vectorized, skipping runs of inert
     bytes) and passed to the parse, which no longer rescans.
   - A body bounded at `SHALLOW_DEPTH` parses without `serde_stacker`'s
     per-level probe.
   - zod schemas are built once (they were rebuilt per request and per block).
   - Unbounded strings skip the code-point count.
   - A valid UTF-8 body becomes the `String` without the lossy copy.
5. **Routing's token estimate.** One walk now yields both totals,
   bit-identical to the two-walk version.
6. **SSE egress.** After the first frame, every already-decoded event is
   coalesced into one body frame (≤ 64 KiB), without waiting.
7. **Boot.** The field-key KDF runs concurrently with the store open.
8. **THP.** `prctl(PR_SET_THP_DISABLE)` at start, because with THP `always`
   mimalloc's arenas were resident in 2 MiB pages. Idle RSS 17.5 → 10–12 MiB.
9. **mimalloc v2** instead of v3: lower retained memory, as the table above
   shows.
10. **`bench-gateway.ts`** resolves a relative `--gateway`.

Behaviour did not change. Evidence:

- `cargo test --workspace`: 439 passed.
- The conformance e2e on the final binary: every row equal (client bytes,
  upstream bytes, and DB rows).

## Caveats

- Loopback only, as for the baseline.
- The tails depend on the host, as shown above. Rerun on a quiet host before
  quoting p99.
- `omni keys list` measures the TS CLI.
