# Gateway: Rust slice 1, single process

The first benchmarkable slice of the Rust gateway (single mode, SQLite) is
measured here against the [TypeScript baseline](2026-11-07-ts-baseline.md) and
against the spec's targets (`docs/superpowers/specs/2026-11-07-rust-gateway-migration-design.md`,
§"Targets"). The raw output is in
[`2026-11-08-rust-slice1.json`](2026-11-08-rust-slice1.json): the summary, the
three runs in full, and earlier zero-drop measurements.

**Historical measurements of the previous implementation (`ca80bcfa`).**
The revised round-3 writer, limiter and boot-seeded ID generator have not
been benchmarked here. All measured results and target verdicts below refer
to that previous implementation; a fresh median-of-three rerun is pending.

Slice 1 has no cluster mode, because Rust has no Postgres or Redis store yet.
The cluster targets are explicitly **DEFERRED** below.

## Read this first: zero dropped rows at full throughput, with time-ordered ids

- **Every Rust scenario in the headline table reported zero dropped rows.** The table is
  the median of three full, uncapped runs (min–max in brackets) at
  `ca80bcfa`. In every scenario of every run:
  - the writer's barrier reported 0 events dropped and 0 failed, with
    `committed == events`;
  - the request log had 0 rows missing and 0 pending.

  The "rows dropped" column sums these over the three runs. The event counts
  in brackets are the barrier's per-scenario events.
- **Request ids differ from TS.** Rust mints `req_` + an RFC 9562 UUIDv7: a
  millisecond timestamp in its first 48 bits, monotonic within the process
  (RFC 9562 method 3: ids within one millisecond increase by a random step,
  hiding exact intervening counts but permitting statistical rate estimates).
  The 48-bit timestamp representation ends in year 10889; timestamp
  accuracy and monotonicity are not guaranteed across that boundary.
  TS mints `req_` + UUIDv4. This is an operator decision recorded in the spec
  (§Writes, "Request ids: time-ordered"). The `req_<uuid>` shape and every id
  derived from it are unchanged. The conformance e2e accepts either version
  at the id paths, and holds TS to v4 and Rust to v7.
- **Why the ids matter here.** `request_logs.id` is the table's primary key.
  Random v4 ids scattered every insert across that index, so the writer
  committed only 20–25 k req/s on these 4 cores without dropping rows. That
  forced the previous version of this document to cap the bench at 20 k (and
  the version before it published numbers from shedding runs). With v7 ids
  the writer keeps up at the gateway's full rate.
- **The host was quiet.** Before each run, `top` showed no headless Chrome
  load (its GPU process at 0.0 %), and the calibration loop timed every vCPU
  at 461–489 ms alone and 529–596 ms together (raw JSON ranges).

## How it was measured

The rig and method are the baseline's:

- **Script:** `scripts/bench-gateway.ts`, black-box.
- **Upstream:** two `bench-gateway-upstream.ts` processes on one port, reached
  through a `custom` credential.
- **Host:** i5-13400, 8 vCPUs, Linux 6.12, running as a KVM guest. Gateway
  pinned to cores 0-3, upstream to 4-5, `oha` to 6-7.
- **Duration:** 20 s per scenario after a 3 s warmup, with `OMNI_LOG_LEVEL=warn`.
- **Setup:** done by the TS `omni` CLI. The CLI is not ported, so `omni keys
  list` still measures TS.
- **Build:** `ca80bcfa`: release profile, fat LTO, one codegen unit,
  `panic=abort`, mimalloc v2.

```sh
cargo build --release -p omni-gateway
bun scripts/bench-gateway.ts --gateway "$PWD/target/release/omnigateway" \
  --cli "bun apps/cli/src/index.ts" --out run-N.json   # × 3, no --rate
```

Measurement protocol used by the historical runs (`ca80bcfa`):

- **A writer barrier and row accounting per scenario.** The gateway runs
  with `OMNI_BENCH=1`. Only then does the Rust gateway serve
  `POST /__omni/bench/flush`.
  - **Sequencing.** Every event handed to the writer takes a sequence number
    before it is published (or counted as dropped). The barrier's watermark
    is the last number at its admission.
  - **The answer.** The barrier answers once every event up to the watermark
    is resolved, with `{watermark, committed, failed, dropped}` for exactly
    that prefix: `committed + failed + dropped == watermark`.
  - **Admission.** The barrier enters the writer's queue by the same
    non-blocking `try_send` as any event, and only one may be in flight.
    Otherwise the route answers `inconclusive`:
    - 409 when another barrier is in flight;
    - 503 when the queue is full;
    - 504 after the server's 30 s deadline.
  - The harness calls the barrier at each scenario's start and end, so the
    scenario's events, drops and failures are exact deltas, wherever in the
    scenario they happened.
  - After the end barrier the harness counts the `request_logs` rows whose
    `at` falls in the scenario's window:
    - `missing`: answered requests without a `done` row;
    - `pending`: rows never finished.
  - An inconclusive or incoherent answer, or no answer within 60 s, marks
    the scenario `INCONCLUSIVE`, which is flagged and never counted as zero. A gateway
    without the route (TS, which writes synchronously) is checked by the rows
    alone.

  Any non-zero count, or an inconclusive barrier, flags the scenario
  `⚠ DROPPED` and puts a warning at the top of the run. The cancel scenarios
  file a 499 row for each abandoned request, which can hide a missing row
  from `missing`. The drop delta catches that case.

- **`-t 30s`** on every scenario that has no timeout of its own. A wedged
  keep-alive connection becomes a counted error instead of an `oha -w` that
  never returns. held-streams and the cancel scenarios keep their own
  timeouts.
- **Host calibration.** Before the run, a fixed CPU-bound loop is timed on
  each vCPU, first alone and then on all eight at once. During each scenario
  the bench samples the gateway cores' MHz, the busy cores used by processes
  outside the bench (`foreignCores`), and the per-thread CPU and run-queue
  time of the gateway.
- **`--rate N`**: caps every duration scenario at N req/s. It is not used for
  the table below.

### held-streams RSS: previous implementation within target

- **Measured.**
  - **73 MiB** (70–75) in the full run, against ≤ 80;
  - **57 MiB** run alone on a fresh gateway;
  - **74 MiB** right after rate-limited-key, which itself now peaks at
    60 MiB.
  
  The previous round measured 101 MiB (96–102), 59 MiB and 116 MiB for the
  same three cases.
- **What it was.** The scenario starts on the heap that rate-limited-key
  leaves behind, and mimalloc keeps the freed pages. That scenario serves
  ~51 k req/s against the bench key (`requests:1m=100000000`,
  `tokens:5h=1e11`):
  - its `1m` sliding window held one `f64` per request, ~3 M stamps;
  - each long window's row stamps grew to their 2^20 cap.

  All of that scaled with the request rate.
- **Current code, not yet remeasured** (round-3 L1/L2). Minute
  history has a fixed entry cap independent of configuration:
  - **Run-length stamps.** The `1m` window holds equal stamps as one
    `(stamp, count)` entry. The gateway's stamps are whole milliseconds, so a
    minute is at most 60 000 entries whatever the rate.
  - **Configuration-independent history.** Lowering, raising, disabling or
    enabling a minute limit never discards previous admissions. Every subject
    with any configured limit records minute history, including concurrency-only
    subjects, matching TS. A highest-seen-limit ring would not suffice for an
    arbitrary future increase. Fixed small-limit cases remain exact.
  - **A fixed cap of 65 536 exact entries.** Overflow switches to 1000-ms
    buckets represented at their exclusive ends, with up to 61 overlapping
    buckets for a minute. Ordered finite timestamps overcount by at most
    the trailing bucket's count; backward clocks deliberately over-refuse.
    See [limiter compatibility](../limiter-compatibility.md) for the precise
    assumptions and reset/seed truncation caveats.
  - **Long-window row stamps** (for a refusal's exact reset) are capped at
    65 536 instead of 2^20. Only a window holding more rows than that when it
    refuses reports a later `Retry-After` than TS, which reads the oldest row
    from the store. TS's own `1m` ring has no such bound: at this rate it
    would hold the same 3 M stamps.
  - The deques give memory back once a burst ages out.
- **Unchanged.** The ratelimit parity vectors (TS step for step) and the e2e
  `rate limit 1m hit` and `concurrency limit hit` rows pass. The load
  registry (bounded at 10 000 pairs with a TTL) and the long-window `Buckets`
  (one per grain: 300 for 5 h, 168 for 1 w) were checked: neither grows with
  the rate.

## The writer's capacity

The spec's shed path is for real overload, such as a stalled database. It is
not meant to fire at the gateway's own throughput. The historical headline
runs reported no drops; revised code still awaits performance validation.

### What changed across the rounds

- **Time-ordered request ids** (`c23596ed`, `91e7380f`): `req_` + UUIDv7,
  RFC 9562 method 3. Within one millisecond, `rand_a`‖`rand_b` grows by a
  random step of 1–2^56. A step past 2^74 moves to the next millisecond. Only
  the request id changed: it is the one hot primary key on the write path.
  The node id, `tool_use` ids, and key and credential ids stay v4. Current
  code seeds the actual process-global request-ID CSPRNG fallibly from OS
  entropy at boot; failure refuses boot with a clear error.
- **4096-event batches** instead of 512.
- **A 10 000-page `wal_autocheckpoint`.** It is a trigger, not a bound: an
  open reader can still let the WAL grow past it.
- **No read-back.** Roll-ups and limiter debits are computed from the rows the
  batch wrote. The TS comparison test holds the rows equal.
- **Statements with fixed row counts** (256/64/16/4/1), reused across batches.
- **A checkpoint thread**, `wal_checkpoint(PASSIVE)` every 20 ms, off the
  commit path.
- **A 131 072-event queue**: ~1.18 s at 55,491 req/s × 2 events/request. The slots
  take 360 B each (~45 MiB when full), plus each event's own strings.
- **Rate-limit windows bounded independently of configuration** (round 3,
  not yet remeasured); see the
  held-streams section above.

## Host calibration

The three historical raw runs report 461–489 ms alone and 529–596 ms with
all eight vCPUs together; scenario `foreignCores` ranges from 0.15 to 1.17.
These ranges do not support a blanket ±2 % claim. All sampled MHz values
are 2496, the guest-reported value, not a measurement of host turbo frequency.
Earlier bimodality and withdrawn shedding evidence remain in the internal
Task 6b report; they are not published throughput results.

## Caveats

- Loopback only, as for the baseline.
- The disk is a QEMU virtual HDD on XFS. Its fsync stalls (0.5–1 s) are
  absorbed by the writer's queue.
- Rust request ids are UUIDv7 and TS's are v4; see "Read this first".
- `omni keys list` measures the TS CLI.
